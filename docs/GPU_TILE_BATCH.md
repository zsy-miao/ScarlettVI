# Batched native GPU tile mapping

**Status:** independently authored host-side Windows D3D12 helper verified on an NVIDIA GeForce RTX 5060 Ti. This is not Xbox GPU page-table emulation, Xbox memory coherency, or console texture tiling.

## Why batching is supported

Microsoft's public [ID3D12CommandQueue::UpdateTileMappings](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12commandqueue-updatetilemappings) documentation permits multiple **physical heap ranges** to map a contiguous **virtual tile region** in **one reserved D3D12 resource**. It does not allow one mapping call to span different native D3D12 resources.

ScarlettVI's logical 16/24 GiB GPU windows are partitioned into ≤4 GiB native D3D12 reserved-buffer resources. To map logical guest tiles near 4 GiB and 12 GiB, two separate native calls remain necessary, one per native resource.

## New host API

`SparseGpuWindows::map_tile_selection(queue, window_index, guest_byte_offset, heap, physical_tile_indices)` accepts a span of **distinct physical heap tile indices**, one for each adjacent logical GPU tile.

Validation requires a real queue/heap, an aligned and nonempty region of at most 4096 tiles, all selected physical indices inside the heap with no duplicates, no existing guest mappings, and **no crossing native 4 GiB resource-segment boundaries**. Rejected requests perform no D3D12 mapping update.

The implementation uses one `D3D12_TILED_RESOURCE_COORDINATE`, one linear `D3D12_TILE_REGION_SIZE` and N `D3D12_TILE_RANGE_FLAG_NONE` ranges, each with its independent heap start index and one-tile range count. The heap COM reference is retained before the asynchronous native operation is enqueued, and host mapping bookkeeping is rolled back on allocation failure.

The helper counts actual native map/update calls (`native_map_update_calls`), distinguishing API invocations from the number of virtual or physical tiles. `unmap_tiles` supports one contiguous NULL mapping per resource and is now counted separately (`native_unmap_update_calls`).

**Important:** Native `UpdateTileMappings` returns `void`. A successful ScarlettVI HRESULT confirms validation and enqueue only; it does **not** prove the GPU performed the mapping. Callers must fence the queue and verify resulting GPU data before using or retiring physical tile memory.

## Real hardware fixture

Run the dedicated CLI mode:

```powershell
.\build\x64\Release\ScarlettVI.exe gpu-tile-batch
.\build\x64\Debug\ScarlettVI.exe gpu-tile-batch
```

The fixture reserves two logical 16 GiB guest GPU windows, creates one real 1 MiB D3D12 DEFAULT heap containing **16 physical 64 KiB tiles**, and uses one upload buffer and one readback buffer.

1. **Validate failure cases:** null queue, empty tile selection, misaligned guest offsets, nonexistent GPU window, duplicate physical indices, out-of-range heap tile index, and a request crossing the 8 GiB native segment boundary. None produces a host D3D12 mapping update.
2. **First mapping pass:** select physical tile indices **[6, 2, 9, 0]**. Map four consecutive guest tiles beginning at **4 GiB + 5 × 64 KiB** into one reserved resource in **one native call**. Map their second aliases at **12 GiB + 11 × 64 KiB** in one more call. Verify eight mapped virtual tiles and reject overlapping mapping as `ERROR_BUSY`.
3. Fence both mappings, fill each 64 KiB page with different original generated bytes, upload all **262,144 bytes** to the source GPU alias, issue a real D3D12 resource-aliasing barrier, and read back through the other native reserved resource. Compare every byte.
4. Unmap each four-page resource range with one NULL-mapping call and fence before physical tile reuse. Assert zero live GPU mappings.
5. **Second mapping pass:** reorder the physical heap indices to **[0, 9, 2, 6]**, repeat with a second generated payload, fence and verify another **262,144 bytes**, then fence all NULL mappings again.

**Verified Release result on RTX 5060 Ti:** PASS, **two GPU copy submissions**, **four native map calls** and **four native unmap calls**, all **524,288 generated bytes** correct across two passes, with zero live GPU mappings on cleanup.

If the sixteen virtual tile aliases had instead been mapped one at a time, they would require sixteen distinct native mapping calls; this test uses **four**. The same applies to the sixteen NULL tile unmaps.

## Limitations

The existing [GuestGpuPageRegistry](GUEST_GPU_PAGE_REGISTRY.md) still binds pages individually through separate `GpuPageStager` instances. This new method is a validated host primitive to support future registry batch registration grouped by native resource and safely fenced physical tile ownership. It does not yet accelerate existing `GuestGpuPageRegistry::bind` calls.

The user's title executable and local DLLs remain read-only and unexecuted. No original shaders, title entrypoints, DLL initializers or TLS callbacks are executed. Startup readiness remains BLOCKED with 25 unresolved Xbox import references.
