# Reusable Windows GPU page staging

**Status:** native Windows D3D12-backed, verified on the development RTX 5060 Ti. This is a host-side copy and synchronization component, **not** the Xbox memory-management ABI, unified physical memory, or console shader translation.

## Why extract it?

The earlier GPU-to-XMem integration was one large test inside DeviceContext. That made it difficult for a future guest resource translator to request a GPU page readback without copying device ownership, tile mapping, command submission and synchronization code into a new subsystem.

The new independently authored source files are:

- src/gpu/gpu_page_stager.h
- src/gpu/gpu_page_stager.cpp

GpuPageStager owns **or retains a caller-supplied** D3D12 DIRECT queue, along with its own command allocator/list, 64 KiB upload/readback resources, local fence and Windows event. It either owns a standalone 64 KiB GPU heap tile **or retains a caller-owned larger DEFAULT heap with a selected 64 KiB tile index**. Both paths use real Windows GPU memory. It uses an existing SparseGpuWindows logical guest GPU address space, whose native D3D12 reserved buffers are segmented into 4 GiB resources.

The caller supplies the actual Windows ID3D12Device11 and two **different native D3D12 reserved resources** selected by logical guest window indices and 64 KiB aligned offsets. The staging object maps the **same real 64 KiB GPU heap tile** into both native resources via Windows UpdateTileMappings. The guest offset-to-segment translation happens before command recording, so the GPU never receives a synthetic guest GPU VA.

## Public host API

- **open(device, windows, source_window, source_offset, alias_window, alias_offset, optional_shared_queue, optional_shared_heap, heap_tile_index)** validates a real device, two distinct reserved GPU resources, tile bounds and alignment. The supplied queue must be DIRECT and belong to the exact device; a supplied heap must also belong to that device, have DEFAULT/BUFFER-compatible properties and contain the requested tile index. Both native resource aliases map **the same selected heap tile**, and a fence completes both mappings before exposing an open session. It fences mappings before publishing an open session.
- **roundtrip(input_span, output_span)** requires two disjoint host spans of **exactly 65,536 bytes**. It uploads the input to the real mapped tile, performs a resource-aliasing barrier and copies from the second D3D12 alias into readback memory. The GPU queue fence is completed before any output bytes are copied into the caller's buffer.
- **close()** fences prior work, enqueues both NULL tile mappings, fences them, releases all owned D3D12 resources and COM references, and preserves the most recently completed fence number. It is idempotent.
- The same instance can be **reopened after close()** at different logical offsets. Session fence values and submission counters restart with each new queue, and native GPU address translation is rechecked.

The higher-level [GuestGpuPageRegistry](GUEST_GPU_PAGE_REGISTRY.md) now
manages multiple validated frame-to-CPU-alias and GPU-tile bindings, using
one GpuPageStager per bound frame on **one registry-owned shared DIRECT
queue**. The registry's private prepare/readback phases allow multiple
page command lists to be submitted in **one `ExecuteCommandLists` call**,
followed by one fence and staged-result publication. The independent
`gpu-page-registry` test verifies **four frames, eight CPU aliases and
eight GPU tile mappings backed by four different 64 KiB tiles in one
4 MiB shared heap**. All **16 page transfers use seven native queue
submissions**, including three four-page batches and heap-slot reuse
after unbind/rebind. Multi-heap scaling, batched native tile-residency
operations and GPU eviction policies remain future work.

The component does not allocate or free guest XMem physical pages; those remain owned by PhysicalMemory. It does not update CPU aliases during a GPU transfer; callers explicitly stage the completed readback to a CPU alias after verifying it.

## Verification

Run:


        .\build\x64\Release\ScarlettVI.exe gpu-xmem-tiles
        .\build\x64\Debug\ScarlettVI.exe gpu-xmem-tiles


The fixture performs **two independent staging sessions** against two 16 GiB logical guest GPU windows:

1. Open at source logical **4 GiB** and alias logical **12 GiB**. Upload one XMem CPU physical page through a real CPU VA alias, then read through the GPU alias. Verify all **65,536** generated bytes.
2. Upload a different generated 64 KiB page to the same GPU backing, read through the second GPU alias, and prove that **both XMem CPU aliases remain unchanged** until explicitly copying the readback to one CPU alias. Both CPU views then match.
3. Close the staging session, verify both tile mappings are gone, and **reopen the same GpuPageStager instance** at source **4 GiB - 64 KiB** (the last tile in segment 0) and alias **12 GiB + 64 KiB** (tile 1 in a later native segment). Upload/readback a **third distinct 64 KiB payload** and explicitly write it back to the other CPU alias.
4. Explicitly close again and verify all GPU tile mappings are released, all guest physical page aliases agree, and **zero physical pages** leak.

Negative requests are also tested: null device, same-resource mapping, unaligned offsets, nonexistent guest windows, opening an active session twice, attempting to map already occupied tiles from a competing staging object, short input, short output and overlapping input/output spans. Rejected requests cannot silently submit GPU work.

**Observed Release result:** 3 real GPU command-list submissions across 2 independent GPU sessions, 3 × 65,536 byte payloads verified, completed last-session fence **4**, and zero leaked XMem physical pages. Both VS2026 Release and Debug builds are regression-tested.

## Guarantees and limits

The component owns **host D3D12** resources, but not the lifetime of SparseGpuWindows: the caller must keep the passed windows alive until close() or destructor completion. It is not safe to concurrently remap the same guest tile elsewhere during an active staging session. Fence waits have a 10-second timeout; device removal or failure may require a higher-level GPU recovery policy.

The two CPU virtual aliases are genuinely backed by the *same host pagefile section*. The GPU tile is a distinct physical allocation in a real D3D12 default heap; its bytes are **not naturally coherent** with that CPU section. Both directions require deliberate staging. These methods are internal host APIs only; **no XMemTransferMemory, XMemGetWorkingSetStatistics or XMemIsToolsMemAvailable console import** is patched.

Game code, game shaders, title DLL initializers and original assets are not executed or distributed. The existing readiness gate remains blocked with 25 Xbox HLE import references.
