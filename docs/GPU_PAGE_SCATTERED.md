# Scattered GPU page run planning and fenced registration

**Status:** original host-only C++20 Windows x64/D3D12 implementation tested on NVIDIA RTX 5060 Ti. Not Xbox GPU page-table emulation or unified CPU/GPU memory.

## New API

The existing [pinned batch API](GPU_PAGE_BATCH_REGISTRATION.md) only supports adjacent 64 KiB pages within one native D3D12 reserved resource, even though ScarlettVI's logical GPU windows span several native 4 GiB resources. The new original source `src/gpu/guest_gpu_page_scattered.cpp` introduces:

- `plan_scattered(span<PageBinding>, ScatteredPlan&)`: checks guest frame uniqueness, CPU alias alignment, both GPU slots, native resource identities and overlapping slots; sorts requests by logical source GPU address; divides them into maximal runs where **source and alias offsets each advance exactly 64 KiB within the same two native resources**. Planning has no GPU or CPU mapping side effects.
- `bind_scattered(span<PageBinding>)`: checks existing registry conflicts, pins **every** CPU alias in the complete request before the first GPU update, then invokes the established `bind_batch` for each planned run. Each registration retains its own CPU pin, GPU heap-tile assignment and per-frame stager. Outer pins remain through the entire operation.
- `unbind_scattered(span<frame IDs>)`: plans from live frame bindings and issues one acknowledged `unbind_batch` per run. On a failure, completed earlier runs remain retired, while failed and later runs remain owned/pinned.

Each planned run needs **two native UpdateTileMappings calls**, one per GPU alias resource. None spans a native 4 GiB boundary.

### Recovery and limits

On any failed registration run, `bind_scattered` attempts rollback of that run and every prior registered run in reverse order, respecting existing GPU fence safety before releasing CPU pins or reusing heap tiles. If native cleanup itself fails, its live registrations and internal pins remain intact until the caller safely retries. Unbinding multiple native resource runs is **not globally transactional**: after an error, use `heap_tile_for(frame)` to find the remaining live subset for retry. Callers must serialize concurrent mutations to the same registry and sparse GPU windows.

The physical GPU heap is limited to 64 resident 64 KiB slots; the CPU XMem section and the native D3D12 heap remain **separately backed** and require explicit staging.

## Real GPU verification

```powershell
.\build\x64\Release\ScarlettVI.exe gpu-page-scattered
.\build\x64\Debug\ScarlettVI.exe gpu-page-scattered
```

The RTX 5060 Ti test allocates **8 real 64 KiB XMem physical frames**, **16 CPU aliases**, two logical **16 GiB GPU windows**, a single pooled **4 MiB native D3D12 tile heap**, and a shared DIRECT queue.

Eight guest GPU source/alias pairs occur in **four two-page runs**, immediately before and after native 4 GiB and 8 GiB boundaries, with deliberately shuffled input ordering. Planning returns exactly four runs and predicts **8 native map calls versus 16 individual per-page calls**.

The fixture validates:

1. Duplicate frame IDs/slots, unaligned guest offsets, nonexistent windows, and wrong CPU alias/frame ownership fail before mapping; CPU pins roll back completely.
2. All eight pages register with **16 GPU aliases, 16 CPU alias pins, eight distinct physical tile indices, and one real shared D3D12 queue**. Two separate eight-page transfer batches verify **1,048,576 generated bytes** through actual GPU readback; the second batch explicitly writes back to the mirrored CPU alias.
3. Unordered `unbind_scattered` sorts and retires four runs using eight grouped native NULL tile updates with acknowledged fences, resulting in no live mappings or pins.
4. A synthetic mapping-fence timeout on the **third run** occurs after the prior two runs completed. It exercises **six real native mapping calls followed by six real native NULL mapping calls** across reverse-order rollback, with no leaked pins or GPU mappings.
5. Re-registration verifies eight fresh real GPU page readbacks and correct CPU alias contents with CPU writeback disabled.
6. A synthetic failure after one two-page source-group NULL unmap retains all eight pinned frames. Retrying the same scattered input completes the remaining alias-group update without double-unmapping and retires all remaining runs.

**Measured Release result:** **24 verified 65,536-byte GPU page transfers** over **three actual GPU command-list submissions**, **22 native mapping calls** and **22 native NULL unmap calls** (including failure and rollback fixtures). All bytes verified; final XMem physical frames, CPU pins and GPU mappings **zero**.

Synthetic failure injection does not remove or hang the physical GPU; a real device-reset/recreation mechanism is still missing. See [GPU fence recovery](GPU_FENCE_RECOVERY.md).

The game remains **not bootable or rendering**, with 25 Xbox-specific import references unresolved. The user-owned title EXE/DLLs, title entrypoint, callbacks and shaders remain read-only and unexecuted. This is a Windows host GPU virtual-memory research primitive, not an Xbox GPU page-table ABI.
