# Xbox XMemMapPhysicalPagesScatter — independently inferred ABI

**Implementation:** `src/runtime/physical_memory.{h,cpp}` and
`src/runtime/xmem_bridge.{h,cpp}`.

**Status:** original 64 KiB host-backed prototype, validated with generated
fixtures; not yet validated by actual title execution.

## Evidence collected from the user-supplied game (read-only)

Microsoft's `dumpbin /disasm /range` and a local, ignored scratch script
identified the game's `xmem.dll!XMemMapPhysicalPagesScatter` import at IAT RVA
`0x6793A48`. The x64 import trampoline is at RVA `0x5F3FD20`. Two direct
call sites were observed in the original title:

| Instruction VA | Observed arguments | Caller handling |
| --- | --- | --- |
| `0x140B18DDE` | RCX = pointer to virtual-address array at a global, RDX = live element count, R8 = nullptr | Tests EAX nonzero, then clears count |
| `0x140F2CC3E` | RCX = array of 64 KiB virtual addresses, RDX = number of distinct destination addresses, R8 = vector of synthetic page frame numbers | Tests EAX nonzero, otherwise triggers debug assertion |

The second call's upstream code constructs each virtual destination by shifting
an offset left 16 bits (64 KiB granularity), adds a reserved base, and fills a
parallel source-page list. These independently observed callers establish this
limited three-argument x64 convention:

```cpp
BOOL WINAPI XMemMapPhysicalPagesScatter(
    void* const* destinations,
    uintptr_t count,
    const uintptr_t* physical_page_numbers);
```

A null `physical_page_numbers` vector requests unmapping. **Only this caller
pattern has been examined.** Unknown console flags, GPU memory bookkeeping,
paging priorities and other game versions are not assumed to be equivalent
to desktop Win32 behavior.

## How the original host backend works

- Each synthetic physical page maps to a private, Windows pagefile-backed
  64 KiB section object. Its ID does *not* identify real hardware memory.
- `VirtualAlloc2(MEM_RESERVE_PLACEHOLDER)` reserves a virtual range and
  `VirtualFree(MEM_PRESERVE_PLACEHOLDER)` splits it into 64 KiB slots.
- The independent scatter function accepts addresses from **multiple**
  ScarlettVI-managed placeholder regions in one call. It validates all
  addresses, alignment, duplicate destinations, source-page IDs and empty
  destination slots **before** mapping.
- `MapViewOfFile3(MEM_REPLACE_PLACEHOLDER)` maps the requested physical
  backing at each virtual address. The same physical page may appear in
  multiple virtual slots, with true shared writes.
- Mapping failures attempt to roll back completed views through
  `UnmapViewOfFile2(MEM_PRESERVE_PLACEHOLDER)`. Unmap operations preserve
  the virtual placeholder reservation for later reuse.
- The memory manager keeps per-physical-page alias counts so pages cannot be
  freed while still mapped. Placeholder-range release also unmaps live views.
- A separate fix to partial placeholder splitting releases the full trailing
  reservation on split failure rather than leaving a leaked region.

## Verified `ScarlettVI.exe memory-scatter` check

The test uses only data generated by ScarlettVI, **not game assets**.

1. Allocate three synthetic 64 KiB physical pages.
2. Reserve two independent placeholder regions with five virtual slots total.
3. In one three-element scatter call, map page 0 twice at virtual addresses
   from *different regions*, and page 1 at a nonadjacent slot.
4. Verify byte writes and reads through both aliases of page 0.
5. Verify freeing mapped physical pages is rejected.
6. Verify duplicate destination addresses and addresses outside ScarlettVI
   reservations are rejected *before* creating partial mappings.
7. Verify an untouched slot can still be mapped and unmapped afterward.
8. Scatter-unmap all mapped slots and release both reservations and physical
   pages; assert **zero remaining physical pages**.

**Observed result:** `PASS` on the development Windows machine, x64 Release.

The real game's read-only `readiness` report now links one additional
`XMemMapPhysicalPagesScatter` reference and reports **27** unbound Xbox
references. This confirms import-address binding only; it does not establish
gameplay, actual console correctness or GPU-visible physical memory.
