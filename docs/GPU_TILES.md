# Native D3D12 sparse buffer tiles and large guest GPU address windows

**Status:** original Windows D3D12 host tile residency and physical GPU heap
aliasing verified with generated data. **Not an Xbox GPU page-table
implementation**, and not a game shader/texture translator.

## The 4 GiB tile-coordinate boundary observed on the test host

The previous [GPU virtual-memory milestone](GPU_VIRTUAL_MEMORY.md) reserved two
16 GiB or 24 GiB GPU buffer resources directly using Windows D3D12.
Reservation alone works, but GPU tile mapping tests on the development
**NVIDIA GeForce RTX 5060 Ti** revealed an important compatibility detail:

| Tested reserved-buffer tile | Flat D3D12 tile X | Observed GPU readback |
| --- | ---: | --- |
| 64 KiB-aligned offset 0 | 0 | Correct |
| 4 GiB minus 64 KiB | 65,535 | Correct |
| Exactly 4 GiB | 65,536 | Zero data, despite valid fence and no device error |

The same original `UpdateTileMappings` operation and readback were used.
The Windows D3D12 debug layer was enabled. This is a **measured host-driver
boundary**, not a claim that every D3D12 driver or the Xbox GPU has a
4 GiB address limit. The large GPU VA reservation itself remained valid.
No game code was used to diagnose it.

## Segmented native GPU allocations behind continuous guest VA

`SparseGpuWindows` now divides each **logical** 16/24 GiB guest window
into separate Windows `ID3D12Resource` reserved buffers of at most
**4 GiB** each. The public `GuestAddressSpace` registry has one entry
per segment; its keys remain one continuous logical range, even though
native `GetGPUVirtualAddress()` values are not contiguous.

| Logical Xbox-style window | Native Windows GPU resource segments |
| --- | --- |
| 16 GiB | 4 × 4 GiB |
| Two 16 GiB windows | 8 × 4 GiB |
| 24 GiB | 6 × 4 GiB |
| Two 24 GiB windows | 12 × 4 GiB |

For example, logical offset `4 GiB` maps to native segment 1, offset
`0`; logical offset `12 GiB` maps to native segment 3, offset `0`.
Each native segment is independently reserved and consumes no physical
GPU memory until its tiles are mapped.

There is one crucial limitation: **a GPU command that spans two native
segments must be split by a future Xbox command/descriptor translator**.
The original `GuestAddressSpace::resolve` deliberately refuses a native
buffer subrange that crosses resource boundaries. No direct Xbox GPU address
is handed to the Windows driver.

## Real 64 KiB host tile residency and GPU roundtrip

`src/gpu/sparse_gpu_windows.{h,cpp}` contains independently implemented
`map_tiles`/`unmap_tiles` operations:

- Validate window and segment indices, 64 KiB alignment, byte extent,
  tile count, physical heap bounds and duplicate/missing tile slots.
- Use the **native** `ID3D12CommandQueue::UpdateTileMappings` API to map
  ranges from a host `ID3D12Heap` to reserved D3D12 buffer-resource tiles.
- Preserve COM references to mapped heaps and recently unmapped heaps
  until the GPU queue is fenced and the windows are released.
- Reject mapping ranges that cross native segment boundaries; a future
  command translator must issue separate updates.
- Use the documented `D3D12_TILE_RANGE_FLAG_NULL` for explicit unmapping
  once GPU use is complete.

`DeviceContext::tiled_buffer_alias_test` drives a complete GPU roundtrip
using independently generated bytes:

1. Create two logical **16 GiB** guest GPU windows (eight real D3D12
   reserved resources altogether).
2. Allocate a real **128 KiB** D3D12 default heap, with two 64 KiB tiles.
   One tile is used as the test's shared physical backing.
3. Map heap tile 0 to guest window 0 at logical offset **4 GiB**, and
   to window 1 at logical offset **12 GiB**.
4. Verify a second mapping to the same address is rejected; unaligned,
   out-of-heap, cross-segment and unallocated unmap requests are rejected
   before enqueuing GPU changes.
5. Upload and copy **65,536 original generated bytes** into the first
   reserved resource's native segment-local offset 0.
6. Issue a D3D12 **aliasing barrier** and copy the same backing tile from
   the second reserved resource into a CPU readback buffer.
7. Synchronize the actual GPU using a queue fence and compare **every
   returned byte** with the expected input.
8. Enqueue two NULL tile mappings, wait for the final fence, and release
   all GPU buffer resources, tile heap references and VA registry entries.

**Observed on RTX 5060 Ti:** `ScarlettVI.exe gpu-tile-map` returned
**PASS** with 65,536/65,536 bytes matched, one GPU command-list submission
and a completed queue fence. The GPU heap tile is real and physically
backed by a native D3D12 heap. The 16 GiB reserved ranges are **not**
physically allocated.

## Batched selected physical heap tiles

The new original [GPU tile batch test](GPU_TILE_BATCH.md) extends
`SparseGpuWindows` with `map_tile_selection`, mapping **N consecutive guest
virtual tiles to N independently selected physical heap tile indices** in
**one real native D3D12 call per reserved resource**. Each selected physical
index is validated and must be distinct. Existing live guest mappings,
out-of-heap selections, duplicates and native 4 GiB segment crossings
are rejected before enqueueing anything.

`gpu-tile-batch` tests four different physical tiles [6, 2, 9, 0] and
[0, 9, 2, 6], with two guest aliases in different native D3D12 resources,
two real GPU readbacks verifying **524,288 generated bytes**, four total
native map calls and four unmap calls, and zero live tile mappings after
fenced cleanup. This operation has **not** replaced the per-frame registry's
independently fenced bind path.

## Host versus console semantics

This is an **internal host D3D12 capability**. No Xbox page-mapping import
is redirected to `UpdateTileMappings`, and Xbox runtime code has never
executed this fixture.

The host heap's physical tiles are **not shared with** ScarlettVI's
pagefile-backed synthetic `XMemAllocatePhysicalPages` pages.
The CPU/GPU coherency bridge remains a staged upload/dispatch/readback
implementation, not true unified-console-memory mapping.

The 25 remaining console import references, Xbox RDNA2 shader ISA,
XG textures/swizzles, resource descriptor ABI, audio/storage services and
full process startup remain unsupported. The readiness report continues
to say `title_execution_ready=false`.

## Reproduce

```powershell
.\build\x64\Release\ScarlettVI.exe gpu-tile-map
.\build\x64\Release\ScarlettVI.exe gpu-tile-batch
.\build\x64\Release\ScarlettVI.exe gpu-sparse-va
.\build\x64\Release\ScarlettVI.exe gpu-vmem-config 3
.\build\x64\Release\ScarlettVI.exe gpu-vmem-config 4
```

The fixture enables the optional Windows D3D12 debug layer, records any
validation messages if GPU readback fails, and never uses game shader bytecode,
assets or proprietary Xbox SDK libraries.
