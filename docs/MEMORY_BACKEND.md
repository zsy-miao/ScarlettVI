# ScarlettVI console memory layer

**Status: experimental Xbox XMem heap and 64 KiB physical-page virtualization.**

## What works

The C++20 `src/runtime/physical_memory.*` code keeps a host-side registry of
synthetic physical page numbers. Each console 64 KiB page is backed by a
Windows pagefile-backed section object.

`MEM_RESERVE | MEM_RESERVE_PLACEHOLDER` reserves a contiguous virtual address
range. ScarlettVI **lazily splits** 64 KiB placeholder slots only when pages
are actually mapped, so even two 24 GiB regions require few host calls.
`MapViewOfFile3` with `MEM_REPLACE_PLACEHOLDER` maps specific physical
page sections at chosen virtual addresses. Multiple virtual views of the
same section genuinely share storage, without copying the bytes.
`UnmapViewOfFile2(MEM_PRESERVE_PLACEHOLDER)` removes mappings safely.

The independently authored `ScarlettVI.exe memory` fixture verified:
- Allocate two 64 KiB physical pages with the publicly documented API pattern.
- Reserve three contiguous 64 KiB virtual page slots.
- Map two different pages into slots 0 and 1.
- Map a second alias of page 0 into slot 2.
- Write through the first virtual address and immediately read the same byte
  through the alias at the third address.
- Unmap, release the placeholder region, and free the physical backing.
- Query the alias through the original experimental `XMemVirtualQuery`
  bridge and verify real Windows commit/protection/accessibility state.
- Confirm **zero leaked pages**.

ScarlettVI now provides *experimental* links for **12 XMem references** involving
heap allocation, virtual allocation, physical-page allocation/free/map,
non-contiguous scatter mapping and virtual-memory information queries.

The independently authored `ScarlettVI.exe memory-scatter` test validates two
separate virtual reservations, a cross-region aliased physical page, rejection
of duplicate/out-of-range destinations and freeing mapped pages, plus full
unmapping and cleanup. See [XMem scatter call-site analysis](XMEM_SCATTER.md).
The title's host import of `VirtualFree` is transparently routed through
a local adapter which releases ScarlettVI-managed placeholder regions
correctly and delegates all other allocations to Windows.

## Pinned alias lifetimes for host GPU staging

The new original [GuestGpuPageRegistry](GUEST_GPU_PAGE_REGISTRY.md) registers
synthetic physical frames together with **two validated 64 KiB CPU alias
addresses** and two separate native GPU tile slots.

The memory manager provides `pin_mapped_alias(address, frame)` and
`unpin_mapped_alias(address, frame)`, checking frame ownership under its
mutex. Pinned CPU mappings reject XMem unmap, scatter unmap and whole-region
`VirtualFreeBridge(MEM_RELEASE)` requests with `ERROR_BUSY`. Batch unmap
prevalidates every destination so a pinned second slot cannot leave an
earlier unpinned slot partially unmapped. When the registry closes and fences
the native GPU tile mappings, both CPU alias pins are released.

The `gpu-page-registry` fixture tests **four real 64 KiB XMem pages**,
eight CPU alias pins and **eight real D3D12 tile mappings**. All **eight
GPU transfers** verify independently generated bytes; invalid frame/slot
requests and unmap attempts fail before modifying valid registrations.
Final CPU page/pin and GPU tile mapping counts are all **zero**.

These are lifetime protections, **not CPU/GPU coherency or prevention of
concurrent CPU writes**. The GPU tile remains physically separate from
each CPU pagefile-section alias.

## Known limits / warnings

- Synthetic page numbers are private identifiers in 4 KiB frame units;
  they are **not real physical addresses** and cannot be submitted to a GPU.
- Only 64 KiB page mode is implemented; 2 MiB clusters, physical page
  transfer, and working-set statistics remain unsupported. The scatter API
  supports the observed 3-argument caller pattern only and remains unverified
  under title execution.
- Xbox memory allocation attributes are not exhaustively validated; the
  heap branch and ordinary virtual allocation branch remain experimental.
- The current virtual mapping path recognizes
  `MEM_RESERVE | MEM_64K_PAGES`; full graphics access/protection semantics
  are not implemented.
- Lifetime handling for dynamic imports and other DLL-created threads
  still requires further runtime hooks. The `VirtualFree` hook only changes
  the import table entries the custom loader actually patches.
- The test demonstrates host CPU memory aliases, **not Xbox GPU memory
  equivalence** or title runtime stability.
- The query result's +0x30 flags follow an explicitly labelled **desktop**
  compatibility policy, not verified Xbox bit semantics. See the independently
  derived [XMemVirtualQuery call-site analysis](XMEM_VIRTUAL_QUERY.md).
- Xbox SDK implementation-specific details are not included.
