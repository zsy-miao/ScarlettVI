# XG post-creation indirect-call candidate survey

**Status:** original C++20 **read-only byte-pattern** research tool. It is not a complete x64 decoder, an Xbox `XGCreateTextureComputer` implementation, or a verified graphics-object vtable interface. No title instructions, assets or proprietary console SDK components are copied to this repository.

## Scope and reproduction

After the existing [XG import callsite probe](XG_CALLSITE_PROBE.md) verifies the `XGCreateTextureComputer` import thunk and its four observed direct call sites, the new `xg-vcalls` mode extracts up to **128 file-backed executable bytes following each call**, never crossing executable-section boundaries. It searches for the simple `FF /2` indirect-call encoding with an optional x64 REX prefix and an 8- or 32-bit positive qword-aligned base-register displacement.

It does **not** interpret register dataflow or guarantee that a byte-pattern match is an instruction boundary, a real vtable call, or a call on the returned XG object. Indexed and complex addressing patterns are not scanned; offsets outside 0–4096 are filtered out. Confirm suspicious locations independently with an instruction decoder and live object-contract evidence only where legally and technically appropriate.

From the project folder:

```powershell
.\build\x64\Release\ScarlettVI.exe xg-vcalls-fixture
.\build\x64\Release\ScarlettVI.exe xg-vcalls '..\GTA6.Xbox.v1.0.2.1\game_scarlett_master.exe'
```

The generated fixture covers three independent displacement forms (including an REX-extended register), negative displacement, unaligned displacement, SIB-indexed calls, truncated displacement, duplicate windows, overlarge windows, 32-bit overflow and atomic failure. It contains generated bytes only.

## Verified real-title data-only findings

The Release probe found **five candidates** in the four bounded post-create windows. These five byte locations were also checked against **MSVC Dumpbin `/DISASM /RANGE`** in the original title executable (data only), showing matching indirect-call instructions:

| `XGCreateTextureComputer` direct call VA | Candidate indirect call VA | Table-register index | Byte displacement |
| --- | --- | ---: | --- |
| `0x140344235` | `0x140344283` | 10 (`R10`) | `+0x50` |
| `0x140344235` | `0x14034428D` | 0 (`RAX`) | `+0x08` |
| `0x140979C75` | `0x140979C9F` | 0 (`RAX`) | `+0x10` |
| `0x145121A5E` | `0x145121A84` | 0 (`RAX`) | `+0x10` |
| `0x145121A5E` | `0x145121A8F` | 0 (`RAX`) | `+0x08` |

The fourth XG creation site, `0x1416F7141`, had **no matching indirect call in its next 128 bytes**. That does **not** establish that the resulting object is unused or that no indirect calls occur elsewhere.

The immediately preceding read-only disassembly at `0x140344283`, `0x140979C9F` and `0x145121A84` indicates that the relevant table register is loaded from the object pointer. At `0x14034428D` and `0x145121A8F`, the caller again retrieves the pointer before the second indirect call. That is useful evidence of a pointer-to-dispatch-table pattern, **not** proof that the actual Xbox object implements ordinary COM, nor proof of method names, return values, argument widths, lifetime or thread safety.
