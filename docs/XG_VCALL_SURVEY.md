# XG post-creation indirect-call candidate survey

**Status:** original C++20 **read-only byte-pattern** research tool. It is not a complete x64 decoder, an Xbox `XGCreateTextureComputer` implementation, or a verified graphics-object vtable interface. No title instructions, assets or proprietary console SDK components are copied to this repository.

## Scope and reproduction

After the existing [XG import callsite probe](XG_CALLSITE_PROBE.md) verifies the `XGCreateTextureComputer` import thunk and its four observed direct call sites, the new `xg-vcalls` mode extracts up to **128 file-backed executable bytes following each call**, never crossing executable-section boundaries. It searches for the simple `FF /2` indirect-call encoding with an optional x64 REX prefix and an 8- or 32-bit positive qword-aligned base-register displacement.

It does **not** interpret register dataflow or guarantee that a byte-pattern match is an instruction boundary, a real vtable call, or a call on the returned XG object. Indexed and complex addressing patterns are not scanned; offsets outside 0–4096 are filtered out. Confirm suspicious locations independently with an instruction decoder and live object-contract evidence only where legally and technically appropriate.

From the project folder:

```powershell
.\build\x64\Release\ScarlettVI.exe xg-vcalls-fixture
.\build\x64\Release\ScarlettVI.exe xg-vcall-links-fixture
.\build\x64\Release\ScarlettVI.exe xg-vcall-args-fixture
.\build\x64\Release\ScarlettVI.exe xg-vcall-stack-fixture
.\build\x64\Release\ScarlettVI.exe xg-vcall-regs-fixture
.\build\x64\Release\ScarlettVI.exe xg-vcall-followups-fixture
.\build\x64\Release\ScarlettVI.exe xg-vcalls '..\GTA6.Xbox.v1.0.2.1\game_scarlett_master.exe'
```

The generated fixture covers three independent displacement forms (including an REX-extended register), negative displacement, unaligned displacement, SIB-indexed calls, truncated displacement, duplicate windows, overlarge windows, 32-bit overflow and atomic failure. It contains generated bytes only.

The new **table-register provenance signature survey** scans up to **32 bytes before** each previously found indirect-call candidate, looking for a nearby REX.W `MOV r64, qword ptr [r64]` encoding that produces the register used by the indirect call. The second stage revalidates the call's encoded displacement, length and register against the bounded source window rather than trusting supplied metadata. A missing matching load is reported as absent, not inferred. Its separate all-synthetic `xg-vcall-links-fixture` checks valid, missing, malformed, duplicate and out-of-range cases. The scanner deliberately does **not** decode intervening instructions or infer live register values.

## Verified real-title data-only findings

The Release probe found **five candidates** in the four bounded post-create windows. These five byte locations were also checked against **MSVC Dumpbin `/DISASM /RANGE`** in the original title executable (data only), showing matching indirect-call instructions:

| `XGCreateTextureComputer` direct call VA | Candidate indirect call VA | Table-register index | Byte displacement |
| --- | --- | ---: | --- |
| `0x140344235` | `0x140344283` | 10 (`R10`) | `+0x50` |
| `0x140344235` | `0x14034428D` | 0 (`RAX`) | `+0x08` |
| `0x140979C75` | `0x140979C9F` | 0 (`RAX`) | `+0x10` |
| `0x145121A5E` | `0x145121A84` | 0 (`RAX`) | `+0x10` |
| `0x145121A5E` | `0x145121A8F` | 0 (`RAX`) | `+0x08` |

The enhanced `xg-vcalls` output finds **five out of five** local table-register load signatures in these same windows. They all read a qword from **RCX (register index 1)** to the later indirect-call base register. Four table loads are immediately adjacent to their indirect calls; the `+0x50` call at `0x140344283` has **17 bytes** between the end of the load at `0x14034426F` and the call. These five loads also match independently checked Dumpbin instruction locations. This confirms additional local **instruction shapes**, not complete control flow or actual object-pointer identity.

| Indirect call VA | Nearby table-register load VA | Observed load pattern | Intervening bytes |
| --- | --- | --- | ---: |
| `0x140344283` | `0x14034426F` | RCX to R10 | 17 |
| `0x14034428D` | `0x14034428A` | RCX to RAX | 0 |
| `0x140979C9F` | `0x140979C9C` | RCX to RAX | 0 |
| `0x145121A84` | `0x145121A81` | RCX to RAX | 0 |
| `0x145121A8F` | `0x145121A8C` | RCX to RAX | 0 |

The fourth XG creation site, `0x1416F7141`, had **no matching indirect call in its next 128 bytes**. That does **not** establish that the resulting object is unused or that no indirect calls occur elsewhere.

The immediately preceding read-only disassembly at `0x140344283`, `0x140979C9F` and `0x145121A84` indicates that the relevant table register is loaded from a pointer in RCX. At `0x14034428D` and `0x145121A8F`, the caller again retrieves the pointer before the second indirect call. That is useful evidence of a pointer-to-dispatch-table pattern, **not** proof that the actual Xbox object implements ordinary COM, nor proof of method names, return values, argument widths, lifetime or thread safety.

## Bounded RCX/RDX argument-setup evidence

The [new read-only argument survey](XG_DISPATCH_ARGUMENTS.md) searches 24 bytes preceding each verified indirect-call candidate for narrow MOV RCX-from-memory and LEA RDX-from-RSP signatures. It reports **six** locally corroborated setup instructions across four call sites. Both `+0x10` calls have a nearby stack-address preparation in RDX; the two `+0x08` calls reload RCX from a stored pointer. The scanner excludes preceding indirect calls as a conservative register-clobber barrier. None of this proves argument liveness across arbitrary instructions, method purpose, or an Xbox object lifetime rule.

## Outgoing stack writes for the complex +0x50 call

The [bounded stack-write survey](XG_DISPATCH_STACK_SLOTS.md) now independently corroborates three MOV stores at `0x140344272`, `0x14034427A`, and `0x14034427E`, respectively writing R8 (8 bytes) to `[RSP+0x30]`, ESI (4 bytes) to `[RSP+0x28]`, and RAX (8 bytes) to `[RSP+0x20]` before the `+0x50` indirect call at `0x140344283`. The scanner is conservative and does not claim the values, argument types, function semantics or a COM/Xbox ABI.

## Local +0x50 register timeline

The [bounded register-timeline survey](XG_REGISTER_TIMELINE.md) correlates six independently disassembled REX.W LEA/MOV register patterns leading into the `+0x50` dispatch. Its chronological query distinguishes R8's source at the earlier `[RSP+0x30]` store (`RSP+0xA0`) from the later copied R14 source at the call (`RSP+0x58`). This remains *pattern-chain evidence*, not proof of live values or a complete ABI.

## Immediate +0x08 dispatch successors

The [bounded dispatch successor survey](XG_DISPATCH_SUCCESSORS.md) correlates **two** strict `+0x08` follow-up patterns: `+0x50` → `+0x08` and `+0x10` → `+0x08`. Each fully decodes the inter-call gap as an RCX object-slot reload and an RAX table load, then finds an earlier matching *storage-address expression* for the first call. This does not prove identical live pointers across the first call, an object's ownership transition, a return-value contract or `Release` semantics.
